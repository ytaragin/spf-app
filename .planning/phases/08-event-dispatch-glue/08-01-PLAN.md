## Phase Goal

**As a** player in a live game, **I want to** see the resulting game state as soon as a play is run
by either side, **so that** my screen reflects the authoritative server state without a manual refresh.

<objective>
Deliver the first end-to-end vertical slice of the WS event path: an incoming `PlayRun` event is
routed by a new pure dispatch module into a new `applyPlayResult` store action, which funnels the
carried `GameState` through the Phase 7 keystone reducer and pushes the play onto `playResults`
only when the reducer actually advanced (EVT-02 `PlayRun`, EVT-03).

Purpose: `PlayRun` is the highest-value variant and the only one named by EVT-03. Landing it first
proves the whole pipeline (envelope → dispatch → store action → reducer) with a real user-visible
outcome before the remaining four variants are wired.

Output: `src/game/gameEventDispatch.js` with the `PlayRun` branch, `applyPlayResult` on
`gameStore`, `fetchPlayResult` refactored to call it, and per-variant tests against a fake store.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WebSocket server → `dispatchEvent` | Untrusted remote JSON crosses here. The payload is attacker-shaped from the client's perspective; `parseEvent` (Phase 6) has validated only the envelope tag, not the inner `data`. |
| `dispatchEvent` → `gameStore` state | The only place untrusted remote data becomes application state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01 | Tampering | `dispatchEvent` PlayRun branch | high | mitigate | Validate `data` and `data.new_state` are non-null objects before any store call; on failure log and return `false` with zero store actions invoked (D-08). Asserted by `expect(store.calls).toHaveLength(0)`. |
| T-08-02 | Tampering | `gameState` write path | high | mitigate | Every `GameState` write funnels through `applyGameState`, which rejects any state whose `play_counter` is not strictly newer — a forged stale/replayed state cannot regress the UI (Phase 7 keystone, success criterion #3). |
| T-08-03 | Tampering | `applyPlayResult` → `gameState` | medium | mitigate | The incoming object is assigned as a whole new reference by the reducer; no `Object.assign`/spread of attacker-controlled keys into an existing object, so no prototype-pollution merge surface is introduced. Asserted by the absence of `Object.assign`/spread in the apply path. |
| T-08-04 | Information disclosure | `console.error` in `dispatchEvent` | medium | mitigate | Log messages interpolate only the event tag and `typeof`; no payload, no `JSON.stringify`. Asserted by the `.not.toContain('top-secret-value')` test (D-08, Phase 6 D-06). |
| T-08-05 | Denial of service | `dispatchEvent` | low | accept | A malformed-event flood costs one `console.error` per event on a single-threaded client-side SPA with no auth or server-side cost. Rate limiting is disproportionate at ASVS L1. |
| T-08-06 | Elevation of privilege | dispatch → store `set*` actions | high | mitigate | `dispatchEvent` may reach only `apply*` (local, no I/O) actions; a remote event must never be able to trigger a client→server POST. Asserted by `grep -c 'store\.set[A-Z]' src/game/gameEventDispatch.js` returning 0 — a pattern that holds under every branch taken in this phase, including 08-03 Task 3's fallback, which is constrained to the `apply*` surface (D-05, D-06). |
